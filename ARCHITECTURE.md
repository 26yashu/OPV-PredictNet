# OPV-PredictNet — System Architecture & Integration Specification

**Project Title**: OPV-PredictNet — AI-Driven Molecular Screening and Performance Optimization for Organic Photovoltaic Solar Cells  
**Architecture Status**: Phase 1 Initialization  
**Target Environment**: Windows 10/11, 8 GB RAM, Python 3.11, Node.js LTS, SQLite  

---

## 1. Executive Summary & Foundational Scientific Principle

OPV-PredictNet is a specialized scientific software platform designed to accelerate the discovery, evaluation, and optimization of donor and acceptor materials for bulk-heterojunction (BHJ) organic photovoltaic (OPV) solar cells.

### Crucial Scientific Distinction & Domain Axioms

A core failure in naive machine-learning models for organic electronics is the conflation of single-molecule quantum properties with complex thin-film device efficiencies. OPV-PredictNet formally enforces strict architectural and ontological boundaries between four distinct scientific concepts:

```
+-----------------------------------------------------------------------------------------------+
|                                    1. MOLECULAR CANDIDATE                                     |
|  - An individual chemical entity (either a donor polymer/small-molecule or an acceptor/NFA).   |
|  - Defined by SMILES, IUPAC name, structural formula, and molecular graph topology.           |
|  - Possesses intrinsic properties: Molecular Weight, TPSA, gas-phase/isolated HOMO & LUMO.    |
|  * AXIOM: An isolated molecule alone DOES NOT possess a Power Conversion Efficiency (PCE).     |
+-----------------------------------------------------------------------------------------------+
                                                |
                                                v
+-----------------------------------------------------------------------------------------------+
|                             2. DONOR-ACCEPTOR MATERIAL COMBINATION                             |
|  - A physical mixture/blend of two materials forming a bulk heterojunction active layer.       |
|  - Defined by blend ratio (e.g., 1:1.2 wt/wt), energetic offsets (ΔHOMO, ΔLUMO), and          |
|    complementary optical absorption profiles across the solar irradiance spectrum.            |
|  * AXIOM: Material combinations determine exciton dissociation driving force and band offset. |
+-----------------------------------------------------------------------------------------------+
                                                |
                                                v
+-----------------------------------------------------------------------------------------------+
|                                3. EXPERIMENTAL OPV DEVICE RECORD                              |
|  - A physical macroscopic device fabricated in an experimental laboratory.                    |
|  - Complete stack architecture: Substrate / Anode / Interfacial Buffer / Active Layer /        |
|    Cathode Interlayer / Metal Cathode (e.g., ITO / PEDOT:PSS / PM6:Y6 / PFN-Br / Al).         |
|  - Process history: Solvents (CF, CB), additives (DIO, CN), film thickness, thermal annealing.|
|  * AXIOM: Device efficiency is an emergent property of the entire fabricated device stack.    |
+-----------------------------------------------------------------------------------------------+
                                                |
                                                v
+-----------------------------------------------------------------------------------------------+
|                              4. PREDICTED DEVICE PERFORMANCE VALUE                            |
|  - A statistical, data-driven regression estimate of device-level figures of merit:           |
|    Power Conversion Efficiency (PCE), Voc (V), Jsc (mA/cm²), and Fill Factor (FF).            |
|  - Generated by machine learning models trained on published, standardized experimental data  |
|    (AM1.5G, 100 mW/cm², 25°C), bounded by domain-of-applicability and prediction intervals.  |
|  * AXIOM: Predictions are screening estimates, not absolute thermodynamic guarantees.        |
+-----------------------------------------------------------------------------------------------+
```

```

        |
        |  (1) 3D Molecular Canvas (3Dmol.js / Three.js / R3F)
        |  (2) Multi-Target Dashboard (Recharts: PCE, Voc, Jsc, FF)
        |  (3) Screening & History Exploration
        |
        +================ HTTP / REST (JSON & JWT) ================+
        |                                                          |
        v                                                          v
[ FastAPI Router / Gateway ]                               [ Static Assets / CDN ]
        |
        +---> /api/health           (Service Health & Environment)
        +---> /api/auth/*           (User Registration, Login, Token Refresh)
        +---> /api/predictions/*    (Prediction Submission, History, Query)
        +---> /api/chatbot/*        (Local Knowledge Search & Inquiries)
        |
        |-- [ Middleware ]: CORS, Request Validation, Error Handling, JWT Auth
        |
+-------+-----------------------------+-----------------------------+
|                                     |                             |
v                                     v                             v
[ Database Subsystem ]       [ Molecular Subsystem ]       [ ML Subsystem ]
- SQLite (Local ACID)        - RDKit Integration           - Joblib Model Registry
- SQLAlchemy 2.0 ORM         - SMILES Canonicalization     - Random Forest Regressors
- Users, History, Libs       - Descriptor Extraction       - Scaffold-Split Pipelines

                                                            |

                                                   - Offline Knowledge Base
                                                   - Rule & Text Vector Matching
                                                   - Zero Paid API Dependency
```

## 3. Subsystem Responsibilities

### 3.1 Frontend Subsystem (`frontend/`)
- **Technology Stack**: React 19, TypeScript, Vite, Tailwind CSS, shadcn/ui, Three.js, React Three Fiber, 3Dmol.js, Recharts.
- **Responsibilities**:
  - Provide an intuitive, responsive user interface designed to run smoothly on desktop hardware with 8 GB RAM.
  - Present three distinct molecular input mechanisms: manual SMILES entry, molecular file upload (`.mol`, `.sdf`, `.pdb`), and selection from an internal curated library.
  - Render interactive 3D molecular conformations using 3Dmol.js and Three.js canvas.
  - Display predicted solar cell metrics ($PCE$, $V_{OC}$, $J_{SC}$, $FF$) using Recharts visual gauges and radar plots.
  - Maintain client authentication state using secure memory/HTTP-only tokens.
  - Communicate transparently with the backend REST API, reflecting real network state without simulating false successes.

### 3.2 Backend Subsystem (`backend/`)
- **Technology Stack**: Python 3.11, FastAPI, Pydantic v2, SQLAlchemy 2.0, Uvicorn.
- **Responsibilities**:
  - Expose high-performance, asynchronous REST endpoints conforming strictly to `API_CONTRACT.md`.
  - Validate and normalize incoming requests via Pydantic schemas.
  - Manage application configuration and secrets using Pydantic Settings and environment variables.
  - Enforce cross-origin resource sharing (CORS) rules allowing authorized local Vite clients.
  - Protect sensitive endpoints through JSON Web Token (JWT) verification.
  - Coordinate inter-subsystem data flow between molecular parsing, ML prediction, and SQLite persistence.

### 3.3 Molecular Processing Subsystem (`backend/app/services/molecular.py` & `ml/src/features/`)
- **Technology Stack**: RDKit (Python 3.11).
- **Responsibilities**:
  - Parse, sanitize, and canonicalize donor and acceptor SMILES representations.
  - Detect invalid chemical structures, incorrect valences, and unparseable input files early, returning descriptive HTTP 422 errors.
  - Extract 2D physicochemical descriptors (Molecular Weight, LogP, TPSA, aromatic ring count, rotatable bonds, hydrogen bond donors/acceptors).
  - Compute circular fingerprints (Morgan fingerprints / ECFP4) and count-based substructure representations.
  - Format molecular geometries for client-side 3D rendering.

### 3.4 Machine Learning Subsystem (`ml/`)
- **Technology Stack**: Scikit-Learn, NumPy, Pandas, Joblib.
- **Responsibilities**:
  - Construct donor–acceptor blend feature vectors by computing difference descriptors ($\Delta\text{HOMO}$, $\Delta\text{LUMO}$, topological complementarity) and concatenated molecular fingerprints.
  - Host the primary prediction model: Random Forest Regression (`RandomForestRegressor`).
  - Manage model lifecycle: load serialized `.joblib` models into memory upon startup; warm-serve prediction queries with minimal inference latency (<50 ms).
  - Provide prediction uncertainty estimates based on tree ensemble variance.
  - Strictly isolate training and testing data using molecular scaffold splitting to prevent data leakage.

### 3.5 Database Subsystem (`backend/app/db/` & `backend/app/models/`)
- **Technology Stack**: SQLite, SQLAlchemy 2.0.
- **Responsibilities**:
  - Provide lightweight, zero-configuration local ACID persistence suitable for an 8 GB RAM Windows environment.
  - Store user credentials with Argon2 password hashing; **plaintext passwords are strictly prohibited**.
  - Log user-specific prediction records, associating donor/acceptor structures, process metadata, and predicted values with `user_id`.
  - Maintain the curated molecular library of validated benchmark donors and acceptors.
  - Track active and historical machine-learning model versions and performance metadata.

### 3.6 Local Knowledge Chatbot Subsystem (`backend/app/services/chatbot.py`)
- **Technology Stack**: Pure Python, custom TF-IDF / BM25 / rule-based knowledge retriever.
- **Responsibilities**:
  - Answer user inquiries regarding OPV physics, device metrics ($PCE$, $V_{OC}$, $J_{SC}$, $FF$), molecular descriptors, and usage instructions.
  - Rely exclusively on an indexed local scientific knowledge base located in `docs/scientific_basis/`.
  - **Zero Paid API Requirement**: Must operate completely offline without dependencies on OpenAI, Anthropic, or other paid external LLM APIs.
  - Minimal memory footprint (<100 MB RAM).

## 4. End-to-End System Workflows

### 4.1 Authentication Workflow
```
[ User ] ---> (Submits email & password) ---> [ POST /api/auth/login ]
                                                      |
                                                      v
                                        [ Retrieve user from SQLite ]
                                                      |
                                                      v
                                        [ Argon2 Verify Hash(pwd) ]
                                           /                    \
                                       (Valid)                (Invalid)
                                         /                        \
                                        v                          v
                        [ Generate JWT (HS256) ]             [ 401 Unauthorized ]
                                        |
                                        v
                        [ Return Access Token JSON ]
```

### 4.2 Prediction Submission & Normalization Workflow
The prediction engine accommodates three distinct client input methods, converting each into a single **Normalized Prediction Request**:

```
[ Input Method A: Manual SMILES ]  --+
[ Input Method B: File Upload ]    --+--> [ Normalization Adapter ]
[ Input Method C: Library ID ]     --+           |
                                                 v
                                  [ Normalized Request: ]
                                  - Canonical Donor SMILES
                                  - Canonical Acceptor SMILES
                                  - Optional Process Metadata
                                                 |
                                                 v
                                  [ RDKit Descriptor Pipeline ]
                                                 |
                                                 v
                                  [ Blend Feature Construction ]
                                                 |
                                                 v
                                  [ Random Forest Predictor ]
                                                 |
                                                 v
                                  [ SQLite Prediction Logging ]
                                                 |
                                                 v
                                  [ HTTP 201 Response Payload ]
```

### 4.3 Model Loading and Serving Workflow
1. **Application Startup**: During FastAPI lifespan initialization, the application loads the default active model artifact (`v1.0.0.joblib`) from `ml/models/saved_models/`.
2. **In-Memory Cache**: The model object is retained in application memory as a singleton, preventing expensive disk re-reads.
3. **Inference Execution**: When `/api/predictions` is called, the feature vector is transformed and passed to `model.predict()`.
4. **Thread Safety**: Scikit-Learn estimators are read-only during `predict()`, permitting safe concurrent access across asynchronous worker requests.

### 4.4 User-Specific Prediction History Workflow
1. When an authenticated request arrives, the JWT token is decoded, and `user_id` is extracted.
2. The prediction record is persisted in SQLite with `user_id` foreign key.
3. When querying `GET /api/predictions`, the database applies strict filtering: `WHERE predictions.user_id == current_user.id`.
4. Users cannot view or mutate other users' prediction histories.

## 5. Architectural Non-Functional Requirements

- **Memory Budget**: Entire backend, server, and local chatbot must operate within <1.5 GB RAM, leaving ample headroom on an 8 GB RAM system.
- **Inference Latency**: Predict response within <250 ms for canonical SMILES pairs.
- **Portability**: Works natively on Windows 10/11 with standard PowerShell terminal commands.
